## Architecture statement

The four workers are deterministic Python roles:

1. Reconnaissance normalizes registered/ZAP observations into candidates.
2. Planning matches all applicable approved templates within the frozen Standard budget and records gaps.
3. Execution accepts only server-validated approved-operation references and registered adapters.
4. Verification applies deterministic oracles to evidence and keeps suspected, confirmed, inconclusive, and not-confirmed states distinct.

The Central Orchestrator owns authorization, immutable scope, lifecycle, durable queueing, cancellation, evidence linkage, retries, and finalization. No Red Team LLM or model-provider call is required.

## Known limitations and release boundary

- Only the repository's synthetic `vulnerable-store` target is enabled.
- Only SQLi, reflected XSS, and path traversal are supported.
- Authenticated crawling and arbitrary application import are excluded.
- ZAP is on demand and narrowly gated; broad scanning is excluded.
- The synchronous Starlette `TestClient`/AnyIO portal hangs in the current host environment before Red assertions. The HTTP-only API security suite uses the repository's `httpx.ASGITransport` pattern instead.
- A full-repository Ruff audit reports 569 legacy findings outside this release's affected files; changed and newly added Python files pass Ruff.
- Docker BuildKit reports `FromPlatformFlagConstDisallowed` for the existing Linux/amd64-pinned base image. The line is retained because the isolated build-input verifier treats that exact platform and digest as provenance authority.
- M20's Q6_K DEVELOPMENT feasibility decision remains `INELIGIBLE`; M21 final experiments remain blocked.
